# Set up Digest

This GitHub package is a setup/research companion. Each user owns a separate deployed Site and database. It deliberately contains no MCP endpoint or personal deployment identity. The Site supplies the runtime plugin used on desktop and mobile.

Ask whether to create a backend or connect an existing one only when the user's request does not establish the choice. Use the available Sites tools and read the installed Sites skill for its current creation, storage, identity, source-sync and publication workflow. If Sites is unavailable, help the user enable it; do not substitute a shared hosted server.

## Create a backend

Use the versioned template; do not regenerate the backend from a prose description. Read [the deployment contract](../../references/deployment.md). Run `node scripts/materialize-backend.mjs <absolute-new-directory>` from this plugin's root. The directory must be separate from the installed plugin and from any other deployment.

Register a new private Site only if its generated `.openai/hosting.json` has no `project_id`. Persist the exact returned identity immediately. Preserve `d1: "DB"` and `capabilities: ["mcp"]`. Follow Sites source synchronization, build/package, and private publication with `node scripts/build.mjs` as the template's build command. The build is a dependency-free Worker ESM build; it embeds the UI and includes schema migrations. No model API key is needed for this backend.

Use the plugin generated by Sites. Read `get_site` with `include_mcp_connection: true`; offer the returned plugin through the supported plugin installation UI if needed. Do not create a local proxy, edit global Codex config, or embed a personal endpoint in the distributed package. Installation/authorization may require the user's native UI action.

Verify `backend_info`, then `open_digest` through the new connection. Confirm the library actually renders and a user-entered vote persists before claiming the full panel flow works. Reading the hosted web UI alone does not verify the embedded panel. A desktop test does not verify mobile. Report untested surfaces explicitly.

## Connect an existing backend

Resolve the user's Site using Sites inventory; do not guess a project ID from its URL. Read its MCP connection and connect its existing plugin. Verify `backend_info` reports `product: "digest"`, a compatible version and schema version 1. An arbitrary Site is not a Digest backend. Do not overwrite or deploy to an unrelated Site without the user's explicit request.

A backend URL in native settings cannot rewire a host's MCP connection. Changing backend means connecting the other Site's plugin; it does not migrate records. Do not disconnect the old connection or copy its data unless requested.

Finish with the connected backend, version, verification performed, and any required user installation action. Offer creation of the first digest if the user has not supplied its topic; do not silently seed private data or import other chats.
